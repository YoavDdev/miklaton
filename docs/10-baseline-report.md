# 10 — דוח Baseline: מיקלטון כפי שהוא באמת

> נכתב: 2026-08-17 (YOA-8). מבוסס על discovery מבוסס-ראיות של כל הריפו: 6 סקירות מקבילות (ארכיטקטורה, DB/טננטיות, אימות והרשאות, מסך+משמרות, מוקדן+מחלקות, מקלטים) + מיפוי האירועים הקיים. כל טענה מגובה בקובץ/שורה; מה שלא ניתן לאימות מסומן **UNVERIFIED** (סעיף K). לא בוצע שום שינוי בקוד או בדאטה.

---

## A. תקציר מנהלים

**מה מיקלטון היום, לפי הקוד:** מערכת תפעולית למוקד עירוני של יהוד-מונוסון — Next.js 14 (App Router) + Supabase, פרוסה ב-Vercel, עברית RTL. הליבה העובדת והאמיתית:

1. **מדריך שיחות למוקדן** (call-categories) — המודול הבשל ביותר: קטגוריות פנייה עם מנוע זמינות צד-שרת מלא (חופשות, אי-זמינות, ימים/שעות, שומרי שבת עם זמני הבכל, אסקלציה sequential/parallel) וממשק ניהול עשיר למנהלת המוקד.
2. **המסך** (`/screen`) — תצוגת קיר חיה: שעון, מזג אוויר, שבת, הודעות, חופשות, כוננים (במלחמה), כוח אדם ביטחוני בשטח (כולל עריכת משמרות מהמסך עצמו עם לוג שינויים), ושורת משמרת המוקד הנוכחית.
3. **ניהול משמרות** — שלוש מערכות נפרדות: סידור ביטחון/פיקוח (ייבוא אקסל + פקודת יום), סידור מוקד (ייבוא אקסל), וכוננויות (יומן + טופס WhatsApp חתום + ייבוא אקסל).
4. **אירועי חירום** — יומן אירוע שיתופי עם מפה, משתתפים ואורחים דרך קישור-טוקן. עובד, אבל הוא החור האבטחתי הגדול ביותר (ספק תיקון מאושר — YOA-5).
5. **מקלטים** — המודול המקורי: חיפוש כתובת→מקלט קרוב (Google Geocoding + Haversine) וניהול פתוח/סגור. מקור האמת הוא קובץ JSON סטטי.
6. **ניהול משתמשים ותשתית** — 7 תפקידים, JWT בעוגייה, אישור הרשמות, audit חלקי.

**מנגד:** שלושה דשבורדים שהם 100% דמו (מנכ"ל, פקח, אחראי מקלטים), שכבת API עם ~18 נקודות GET פתוחות לגמרי, בסיס נתונים שלא ניתן לשחזר מהריפו, אפס בדיקות ואפס CI, ומודל רב-רשותי שקיים רק כשלד חלקי בסכמה. המערכת **חד-רשותית בפועל** ואינה בטוחה לפריסה רב-רשותית כמות שהיא (סעיף F).

## B. מפת ארכיטקטורה

```
דפדפן (React 18, Tailwind, RTL)
 ├─ דפים מחוברים (JWT בעוגיית auth-token, 8h) ── middleware.js (Edge, jose)
 ├─ /screen (עוגיית screen-key, שנה) ── polling 10s + Supabase Realtime (anon key)
 ├─ דפים ציבוריים בטוקן: /event/live|join, /duty-form (HMAC), /survey/[token]
 │
 ├─ /api/* — 69 routes, Node runtime. אימות פר-route (requireRole / requireRoleOrScreen /
 │            verifyAuth / HMAC) — ה-middleware לא מכסה API בכלל
 │            Supabase client פר-route: service-role (עם fallback שקט ל-anon ב-44 routes)
 │
 ├─ Supabase: Postgres (45 טבלאות) + Auth (סיסמאות בלבד) + Storage (bucket אחד: event-images,
 │            public) + Realtime (12 טבלאות)
 │
 ├─ שירותים חיצוניים: OpenAI (gpt-4o-mini, knowledge-chat) · Google Geocoding (proxy)
 │            · Open-Meteo (מזג אוויר) · Hebcal (שבת — שני geonameid שונים!) · Nominatim
 │            · unpkg CDN (Leaflet בזמן ריצה)
 │
 └─ פריסה: Vercel (אין vercel.json, אין cron, אין CI). גרסה: build stamp → /api/version →
            AutoRefresh (reload אוטומטי לכל הלקוחות אחרי deploy)
```

עובדות מבניות מרכזיות:
- **אימות היברידי:** Supabase Auth רק לאחסון סיסמאות; ה-session הוא JWT עצמאי (`lib/auth.js`). לכן `auth.uid()` הוא NULL בכל בקשה — RLS מבוסס-משתמש לא ישים במבנה הנוכחי; ההגנה בפועל היא service-role + בדיקות בקוד.
- **נתוני-על בקבצים:** `data/shelters.json` (59 מקלטים), `streets.json`, `zoneAssignments.json`, `alertFlows.json` — עריכה = deploy.
- **State בזיכרון התהליך:** rate limiting, זיכרון שיחת ה-AI, cache שבת — לא שורד cold start ולא משותף בין instances של Vercel.
- **אין בדיקות, אין CI, אין קונפיג ESLint בפועל, אין TypeScript.**

## D. מפת משתמשים ותפקידים — בפועל

7 תפקידים ב-DB + פסאודו-תפקיד `screen`. הרשאות **בפועל** (לא המוצהרות):

| תפקיד | דפים (middleware) | כתיבה ב-API בפועל |
|---|---|---|
| `admin` | הכל | הכל (`requireRole` מעביר admin תמיד) — **חוץ מסקרים!** (בדיקת `=== 'call_center_manager'` קשיחה מחזירה לו 403) |
| `call_center_manager` | operator + שלה | הרחב ביותר: קטגוריות, סידורים, כוננויות, ידע, הודעות, סקרים, security-*, משימות |
| `sector_manager` | שלו | אנשי קשר, מחלקות, כוננויות, כל ה-security-* |
| `operator` | שלו | עדכונים יומיים, הודעות, לחצני מצוקה, סטטוס מקלטים, מצב מלחמה, סגירת אירועים, פקודת יום |
| `ceo`, `inspector`, `shelter_manager` | שלהם (דמו) | **אפס** הרשאות כתיבה ייעודיות |
| `screen` (טוקן) | `/screen` | קריאת כל ה-`requireRoleOrScreen` + **כתיבה לפקודת היום** |

פערי UI-מול-שרת בולטים (מדגם; המלא בדוח האבטחה): `operator/sessions` בלי בדיקת תפקיד בכלל; `operator/tasks` POST/PUT לכל מחובר; `tasks` PUT בלי בדיקת בעלות; `map-data` PUT לכל מחובר על כל אירוע; רישום עצמי מקבל `role` מה-body (נבלם רק ע"י סטטוס pending); מנגנון "חובת החלפת סיסמה" ב-middleware הוא dead code (הדגל לא נחתם ל-JWT).

## E. מפת בסיס הנתונים

**45 טבלאות** בקבוצות: זהות (user_profiles, password_resets, audit_log, system_settings, user_departments) · ארגון (municipalities, departments, contacts) · כוננויות (duty_roster + on_call_contacts/on_call_shifts הישנות) · מדריך שיחות (call_categories + 4 טבלאות בת) · סידור מוקד (call_center_staff/shifts/schedule) · ביטחון (security_staff/shifts/weekly_schedule/daily_orders/daily_order_entries/staff_leave/settings/shift_changes) · אירועים (emergency_events, event_participants, event_journal) · תוכן (knowledge_base, knowledge_chat_history, general_notifications, daily_updates, garbage_collection_schedule, panic_buttons) · סקרים (surveys, survey_responses) · תפעול מוקדן (operator_tasks, operator_sessions, operator_messages) · מצב (war_mode, shelter_status).

ממצאים מבניים קריטיים:
- **הסכמה לא ניתנת לשחזור מהריפו.** `RUN_MIGRATIONS_ORDER.md` מכסה 4 מתוך 70 קובצי SQL; 14 טבלאות נוצרות בסקריפטים מחוץ ל-migrations; שתי מיגרציות `20260510` כפולות שאי אפשר להריץ יחד; מיגרציה הרסנית (`20260511_remove_oncall_tables.sql`) שמעולם לא הורצה ואסור שתרוץ; `operator_tasks` ו-`departments` מוגדרות פעמיים בסכמות סותרות — המצב החי הוא היברידי שאף קובץ לא משחזר.
- **שתי טבלאות רפאים בקוד:** `notifications` (surveys/submit כותב אליה — לא קיימת, נכשל בשקט) ו-`users` (`/api/tasks` עושה עליה join — לא קיימת; ה-route כנראה שבור).
- **טבלאות מתות:** `operator_shifts`, `shift_messages` — אפס שימוש בקוד.
- **RLS אחרי מיגרציית הנעילה — ✅ אומתה כרצה בפרודקשן (2026-08-17):** כל הטבלאות RLS-on ומספרי ה-policies תואמים בדיוק לחלוקה: 32+ נעולות לגמרי; 9 קריאה-בלבד (בשביל Realtime); `user_profiles` עם הרשאות עמודתיות; **3 טבלאות האירועים פתוחות לגמרי ל-anon** (זמנית, עד YOA-5). **המיגרציה לא נוגעת ב-Storage** — ההעלאה הציבורית ל-bucket נשארת. (YOA-6 למעשה הושלם.)
- **Schema drift אמיתי (אומת מול פרודקשן):** בפרודקשן קיימות 3 טבלאות שאף קובץ SQL בריפו לא יוצר — `sector_daily_tasks`, `sector_staff`, `sector_weekly_schedule` (במקביל ל-`security_*`). מחזק את אי-יכולת השחזור (YOA-13).
- **הכפילויות — אומתו מול פרודקשן:** `operator_tasks` החי = Definition A (13 עמודות, עם `municipality_id`) → מתנגש עם `/api/operator/tasks` שכותב סטטוסים בעברית; `departments` = היברידי (9 עמ' + `municipality_id`). `notifications`/`users` (טבלאות רפאים) אינן קיימות גם בפרודקשן.
- **סיסמאות זמניות בטקסט גלוי** ב-`password_resets.temp_password_plain`, ללא ניקוי.

## F. מוכנות רב-רשותית (Tenant Readiness)

**סיווג: לא בטוח לפריסה רב-רשותית (unsafe for multi-tenant deployment).** קיים שלד חלקי — אבל הוא מת בפועל:

1. **זהות הרשות נקבעת בצד הלקוח:** `NEXT_PUBLIC_MUNICIPALITY_ID` (env) → `localStorage` → ואפילו פרמטר URL במסך (`/screen?municipality_id=` נכתב ישר ל-localStorage). ה-JWT לא נושא tenant. אין שום מקור אמת צד-שרת.
2. **בלבול slug/UUID:** ה-env אמור לספק UUID; 9 מ-10 עמודות ה-tenant הן UUID; רק route אחד ממיר slug→UUID. **בפרודקשן `NEXT_PUBLIC_MUNICIPALITY_ID` הוא UUID תקין** (אומת 2026-08-17) — אך ב-`.env.local` המקומי הוא מוגדר פעמיים (UUID ואז `yehud` — ה-slug מנצח), פצצת-זמן אם ישוכפל לסביבה אחרת.
3. **`user_profiles.municipality_id` קיים אך מת:** לא נכתב באף יצירת משתמש, לא נקרא באף שאילתה.
4. **17 טבלאות בלי שיוך רשות בכלל** — כולל כל האירועים, הסקרים, מאגר הידע, סטטוס מקלטים, הודעות, מצב מלחמה.
5. **19 טבלאות עם שרשרת FK לרשות — שאף שאילתה לא עוברת בה**; ו-4 routes מרכזיים (departments, on-call-contacts, panic-buttons, operator/tasks) מחזירים נתונים חוצי-רשות בלי סינון.
6. **אפס אכיפת tenant ב-RLS** — אין ולו policy אחד עם predicate של רשות.
7. **כל קבצי הנתונים** (מקלטים, רחובות, אזורים, flows) חד-רשותיים ללא מפתח רשות; seeds של יהוד קשיחים בתוך המיגרציות.
8. הקוד גם תלוי-שמות-בעברית: המסך מאתר מחלקות לפי `name.includes('בטחון')`/`'מוקד'` — שביר גם בתוך רשות אחת.

**מסקנה לעיצוב:** המעבר לרב-רשותי הוא שכבת יסוד (Phase 2), לא פיצ'ר. הבסיס הנכון: tenant ב-JWT + resolver צד-שרת יחיד + עמודת רשות בכל טבלה + אכיפה בשכבת ה-API (ובהמשך RLS) + נתוני-על ב-DB במקום קבצים/env.

## H. תהליכים קריטיים לפרודקשן — לשמור מרגרסיה

1. **המסך** — כל הצינור: security-daily-order (מיזוג שבועי+יומי, כולל today+yesterday), call-center-schedule/current (חצות, משמרות לילה), notifications, vacations, war-mode, weather; העריכות מהמסך; ה-AutoRefresh.
2. **ייבוא אקסל של סידור ביטחון/פיקוח** — הפורמט האמיתי (גיליון-לשבוע, זיהוי serial תאריך, התאמת שמות fuzzy) והדריסה השבועית המבוקרת.
3. **מדריך השיחות** — מנוע הזמינות (שבת! חופשות! אסקלציה) — הכלי המרכזי של המוקדן בשיחה חיה.
4. **כוננויות** — טופס ה-WhatsApp החתום, יומן מנהל המכלול, והצגה במסך במלחמה.
5. **זרימת מצב מלחמה** — ההדלקה משנה את כל הממשקים (טאבים, FlowRunner, מסך).
6. **חיפוש מקלטים** — geocoding + קרובים ביותר + סטטוס פתוח/סגור (בחירום זה הפיצ'ר המציל-חיים).
7. **ניהול משתמשים** — אישור, השעיה, איפוס.
8. **אירועי חירום** — נמצא בריפקטור מאושר (YOA-5); לשמר את כל היכולות כולל אורחים.

## I. חוב טכני (מה שיכביד על כל פיתוח עתידי)

1. **DB לא משחזר** + אין migration runner + אין schema tracking — חוסם סביבת staging, בדיקות, ורשות שנייה (הפירוט ב-E).
2. **אפס בדיקות ואפס CI** — כל שינוי אבטחה/סידורים נבדק ידנית או בכלל לא.
3. **כפילויות לוגיקה:** חישוב "משמרת פעילה עכשיו" ממומש 5 פעמים עם כללים שונים; timezone מטופל בחלקו בדפדפן (תלוי-שעון-מסך); 3 מערכות אנשי-קשר מקבילות (contacts / on_call_contacts / call_category_contacts) לא מסונכרנות; 2 APIs סותרים לאותה טבלת משימות.
4. **69 יצירות client של Supabase אינליין** במקום helper אחד; 11 clients בדפדפן במקום module משותף.
5. **קוד מת ושבור:** 13 קישורי דשבורד ל-404, `/api/tasks` שבור (join לטבלה לא קיימת), מונה משימות/הודעות שבור אצל המוקדן, 12+ קומפוננטות לא בשימוש, empty route dirs, טמפלט אקסל שהמייבא שלו לא יכול לקרוא.
6. **קונפיג קשיח:** קואורדינטות, geonameids כפולים של Hebcal, שמות מחלקות בעברית כמפתחות לוגיים, עמודות אקסל קשיחות.
7. **שלושה מייבאי אקסל נפרדים** עם רמות חוסן שונות (התיקון מקומיט 0064056 לא הוחל על מייבא המוקד).

## L. מפת דרכים מומלצת

> עיקרון: אינקרמנטלי, בלי rewrite, פרודקשן ממשיך לעבוד. כל פיצ'ר עובר את הצינור: אפיון → ספק → תוכנית → TDD → code review → security review.

### Phase 0 — ייצוב ואבטחה (בעבודה; ~1-2 שבועות)
1. **YOA-5** ריפקטור אירועים (ספק מאושר) — סוגר C1 + חלק מ-C6.
2. **סגירת ה-GET הפתוחים (C2)** — sweep אחד של `requireRole`/`requireRoleOrScreen` על ~18 routes + תיקון פערי H4 (sessions/tasks/map-data) — שינוי קטן, כמעט בלי סיכון רגרסיה (הצרכנים כולם מחוברים או מסך).
3. **Storage policy (C3)** — ביטול INSERT ציבורי (נכנס למיגרציית YOA-5).
4. **הקשחת הרשמה (C4)** — whitelist תפקידים ללא admin.
5. **סיסמאות זמניות (C5)** — `crypto.randomBytes` + ביטול האחסון הגלוי + ניקוי רשומות ישנות.
6. **תיקון H1** (חתימת הדגל ב-JWT) + rate limiting על change-password.
7. **YOA-6** הרצת מיגרציית ה-RLS + **YOA-7** רוטציית סודות (כולל מפתח Google — H6).
8. **YOA-10** דוחות פיקוח ל-Supabase (מתקן גם כתיבה-ללא-אימות) + **YOA-9** אימות קלט.
9. תיקון H8 (מחיקה גלובלית ב-duty-form) — באג מסוכן תפעולית, תיקון ממוקד.

### Phase 1 — מוצר בסיס יציב (~2-3 שבועות)
- **DB משחזר:** איחוד כל ה-DDL למיגרציות ממוספרות + baseline schema + ארכוב המסוכנות/כפולות + runner — תנאי לכל מה שאחרי.
- **CI + בדיקות ראשונות:** GitHub Actions (build + lint מוגדר) + בדיקות API לאימות/הרשאות (החוזה של Phase 0).
- **איחוד תשתיות:** helper אחד ל-Supabase server client (בלי fallback שקט), ספריית זמן אחת (Israel TZ + overnight) שמחליפה את 5 המימושים, ניקוי קוד מת + 404 + `/api/tasks` השבור.
- ניטור שגיאות (Sentry) + תיקוני היציבות הקטנים מתוכנית 08 (redirects, מדיניות סיסמה).

### Phase 2 — יסודות רב-רשותיים (~3-4 שבועות)
- tenant ב-JWT + resolver צד-שרת יחיד; ביטול tenant מ-localStorage/URL.
- `municipality_id` בכל טבלה רלוונטית (כולל אירועים, ידע, סטטוס מקלטים) + backfill יהוד + אכיפה בשכבת ה-API.
- **מקלטים ל-DB** (עם tenant) + ממשק עריכה — סוגר גם את פער ה-deploy-לכל-עדכון.
- קונפיג רשות מ-DB (שם, לוגו, קואורדינטות, geonameid, צבעים) במקום env vars.
- Storage בנתיבי-tenant; seeds פרמטריים; תסריט הקמת רשות חדשה מקצה לקצה (זה ה-acceptance test: להקים "אור יהודה" ריקה).

### Phase 3 — אינטליגנציה תפעולית
- **המסך החכם:** מצבי תצוגה (שגרה/חירום/שבת) עם מנוע תיעדוף, סטטוס מקלטים על המסך, בלוקים מונעי-הקשר.
- דשבורדים אמיתיים: מנכ"ל (KPI מנתונים חיים), פקח (משימות + דוחות אחרי YOA-10), אחראי מקלטים (חיבור ל-shelter_status).
- אירועים v2: תבניות אירוע, סיכומים, תחקירים; איחוד מערכות אנשי הקשר.
- מובייל/PWA לתפקידי השטח.

### Phase 4 — מוכנות מסחרית
- ניהול רשויות (super-admin), onboarding עצמאי, מיתוג פר-רשות.
- Observability מלא, גיבויים/DR, נהלי אבטחה מתועדים, נגישות (WCAG), תיעוד לקוח.
- (החלטת מוצר: תמחור/רישוי — מחוץ לתחום הקוד.)

**הנימוק לסדר:** אבטחה לפני הכל כי הדומיין הציבורי ממתין והמערכת בשימוש חי; DB משחזר לפני רב-רשותיות כי אי אפשר להקים רשות שנייה על סכמה שלא ניתנת לשחזור; רב-רשותיות לפני "מסך חכם" כי כל פיצ'ר חדש שייכתב בלי tenant יעמיק את הבור.
